Postgres is a relational database known for its scalability, reliability, and ease of use. It's one of the most popular databases in the world and one of the reasons for its popularity is the ability to extend the database with custom functions, data types and more using the Postgres Extensions API.

In this post, we'll learn to build a Postgres extension from scratch touching upon all the core concepts. This requires some knowledge of C and Postgres.

At its core, a Postgres extension is a collection of 4 files:
1. The `.c` source code file that contains the C code for the extension.
2. A `.sql` file that contains the SQL code for the extension.
3. A `Makefile` that defines how to build the extension.
4. A `.control` file that serves as a manifest and defines the extension name, version, and dependencies.


## The C source file

This is our main source code for the extension. In our case we will define a simple function to print hello world.

```c
#include "postgres.h"
#include "fmgr.h"
#include "utils/builtins.h"

PG_MODULE_MAGIC;

PG_FUNCTION_INFO_V1(hello_hashlib);

Datum hello_hashlib(PG_FUNCTION_ARGS)
{
    PG_RETURN_TEXT_P(cstring_to_text("Hello from hashlib extension!"));
}
```

Let's break this down and examine each part in detail.

### 1. Header files

- **`postgres.h`** - The main Postgres header that provides core data types, macros, and definitions. This is the foundation that every Postgres extension must include and is defined in [postgres.h](https://github.com/postgres/postgres/blob/master/src/include/postgres.h).
- **`fmgr.h`** - Contains the Function Manager interface, which handles how Postgres calls your C functions. It defines macros like `PG_FUNCTION_ARGS` and `PG_RETURN_*` and is defined in [fmgr.h](https://github.com/postgres/postgres/blob/master/src/include/fmgr.h).
- **`utils/builtins.h`** - Provides utility functions for common operations, including `cstring_to_text()` which we use to convert C strings to Postgres's text type and is defined in [builtins.h](https://github.com/postgres/postgres/blob/master/src/include/utils/builtins.h).

### 2. PG_MODULE_MAGIC

This macro is **mandatory** for all Postgres extensions. It serves as a version check to ensure your extension is compatible with the Postgres server it's being loaded into. Without this, Postgres will refuse to load your extension with an error message.

The magic number contains information about:
- PostgreSQL version the extension was compiled against
- Architecture (32-bit vs 64-bit)
- Floating-point format
- Other ABI compatibility details 

### 3. PG_FUNCTION_INFO_V1

This macro declares metadata about your function to PostgreSQL. It tells the server:
- The function name (`hello_hashlib`)
- That it follows version 1 of the calling convention
- How to properly invoke the function

Think of it as registering your function with PostgreSQL's function registry.

### 4. Function Definition

#### Function Signature

- **`Datum`** - PostgreSQL's universal data type that can hold any PostgreSQL data type (int, text, boolean, etc.). All PostgreSQL functions return a `Datum`.
- **`hello_hashlib`** - Our function name that will be callable from SQL.
- **`PG_FUNCTION_ARGS`** - A macro that expands to `FunctionCallInfo fcinfo`, which contains all the arguments passed to the function and metadata about the call.

#### Function Body

- **`cstring_to_text("Hello from hashlib extension!")`** - Converts a C string literal into PostgreSQL's internal `text` type. PostgreSQL has its own string representation that includes length information.
- **`PG_RETURN_TEXT_P(...)`** - A macro that properly returns a PostgreSQL `text` value. The `_P` suffix indicates we're returning a pointer to the text object.

#### The Complete Flow

When someone calls `SELECT hello_hashlib();` in SQL:

1. PostgreSQL looks up the function using the metadata from `PG_FUNCTION_INFO_V1`
2. It calls our C function with the standard `PG_FUNCTION_ARGS` parameter
3. Our function creates a PostgreSQL text object from our C string
4. We return it using the proper PostgreSQL return macro
5. PostgreSQL handles the memory management and returns the result to the user

This simple example demonstrates the fundamental pattern that all PostgreSQL extension functions follow: receive arguments through the standard interface, process them using PostgreSQL's data types and utilities, and return results using PostgreSQL's return macros.

## The Control File

The control file serves as a manifest for your extension. It contains metadata that PostgreSQL uses to understand how to install, manage, and interact with your extension.

Create a file named `hashlib.control`:

```ini
# hashlib extension
comment = 'Simple hash library extension for PostgreSQL'
default_version = '0.0.1'
module_pathname = '$libdir/hashlib'
relocatable = true
```

Let's break down each parameter:

- **`comment`** - A human-readable description of what your extension does
- **`default_version`** - The version of the extension to install when no version is specified
- **`module_pathname`** - Path to the compiled shared library. `$libdir` is a PostgreSQL variable that points to the library directory
- **`relocatable`** - Whether the extension can be moved to a different schema after installation

## The SQL File

The SQL file defines the SQL interface for your extension. It creates the function signatures that map to your C functions.

Create a file named `hashlib--0.0.1.sql`:

```sql
-- complain if script is sourced in psql, rather than via CREATE EXTENSION
\echo Use "CREATE EXTENSION hashlib" to load this file. \quit

CREATE OR REPLACE FUNCTION hello_hashlib()
RETURNS text
AS 'MODULE_PATHNAME', 'hello_hashlib'
LANGUAGE C IMMUTABLE STRICT;
```

Let's understand what's happening:

- **`\echo Use "CREATE EXTENSION hashlib" to load this file. \quit`** - This prevents the SQL file from being executed directly with `psql`. It should only be run through `CREATE EXTENSION`.
- **`CREATE OR REPLACE FUNCTION`** - Defines the SQL function signature
- **`RETURNS text`** - Specifies that the function returns a text value
- **`AS 'MODULE_PATHNAME', 'hello_hashlib'`** - Links the SQL function to the C function. `MODULE_PATHNAME` is replaced by the path from the control file.
- **`LANGUAGE C`** - Indicates this is a C function
- **`IMMUTABLE STRICT`** - Performance hints. `IMMUTABLE` means the function always returns the same result for the same input, and `STRICT` means it returns NULL if any argument is NULL.

## The Makefile

The Makefile defines how to build the extension. 

```makefile
EXTENSION = hashlib
MODULE_big = hashlib
DATA = hashlib--0.0.1.sql
OBJS = hashlib.o 
PG_CONFIG = pg_config
PGXS := $(shell $(PG_CONFIG) --pgxs)
include $(PGXS)
```

Let's break down what we're doing here:

- **`EXTENSION`** - The name of the extension (must match the .control file name)
- **`MODULE_big`** - The name of the shared library that will be created
- **`DATA`** - The SQL files that should be installed with the extension
- **`OBJS`** - The object files that need to be compiled and linked
- **`PG_CONFIG`** - The path to the pg_config command, which provides build configuration
- **`PGXS`** - PostgreSQL Extension Building Infrastructure. This provides all the build rules.

## Building with Docker

Instead of installing PostgreSQL development packages locally, we'll use Docker to ensure a consistent build environment.

```dockerfile
ARG PG_MAJOR=17
FROM postgres:$PG_MAJOR
ARG PG_MAJOR

COPY . /tmp/pghashlib
WORKDIR /tmp/pghashlib

RUN apt-get update && \
    apt-get install -y --no-install-recommends \
            build-essential \
            postgresql-server-dev-$PG_MAJOR && \
    make clean && \
    make OPTFLAGS="" && \
    make install && \
    cd / && \
    rm -rf /tmp/pghashlib && \
    apt-get purge -y build-essential postgresql-server-dev-$PG_MAJOR && \
    apt-get autoremove -y && \
    rm -rf /var/lib/apt/lists/*
```

Here's what each step does:

1. **`ARG PG_MAJOR=17`** - Sets the PostgreSQL major version (17 in this case)
2. **`FROM postgres:$PG_MAJOR`** - Uses the official PostgreSQL Docker image
3. **`COPY . /tmp/pghashlib`** - Copies our extension source code into the container
4. **`apt-get install`** - Installs the necessary build tools and PostgreSQL development headers
5. **`make clean && make OPTFLAGS="" && make install`** - Builds and installs the extension
6. **Clean up** - Removes build dependencies and temporary files to keep the image size small

## Building and Testing

### 1. Build the Extension

```bash
# Build the Docker image
docker build -t postgres-hashlib .

# Run the container
docker run -d --name postgres-test \
  -e POSTGRES_PASSWORD=password \
  -p 5432:5432 \
  postgres-hashlib
```

### 2. Connect and Test

```bash
# Connect to the database
docker exec -it postgres-test psql -U postgres

# Create the extension
CREATE EXTENSION hashlib;

# Test the function
SELECT hello_hashlib();
```

You should see the output:
```
           hello_hashlib            
-----------------------------------
 Hello from hashlib extension!
```

## Key Takeaways

1. **Extensions are Powerful** - They allow you to add custom functionality directly to PostgreSQL
2. **Four Essential Files** - Every extension needs a .c file, .sql file, .control file, and Makefile
3. **Version Management** - Extensions support versioning through the control file and SQL scripts
4. **PGXS Simplifies Building** - The PostgreSQL Extension Building Infrastructure handles most of the complexity
5. **Docker for Consistency** - Using Docker ensures reproducible builds across different environments

## Best Practices

- **Always include PG_MODULE_MAGIC** - Without it, PostgreSQL won't load your extension
- **Use proper PostgreSQL data types** - Don't mix C types with PostgreSQL types
- **Handle memory management carefully** - Use PostgreSQL's memory contexts
- **Test thoroughly** - Extensions run in the database process, so bugs can crash the server
- **Version your extensions** - Plan for updates and migrations from the beginning

## Conclusion

Creating PostgreSQL extensions opens up endless possibilities for extending your database's capabilities. From simple utility functions to complex data types and operators, extensions allow you to implement performance-critical functionality directly in the database server.

The pattern we've explored - C functions wrapped in SQL interfaces, managed through control files and built with PGXS - forms the foundation for all PostgreSQL extensions. Whether you're building a simple hash function or a complex full-text search engine, these same principles apply.

Start with simple functions like our hello world example, then gradually add more complex functionality as you become comfortable with the PostgreSQL extension API. The database server's extensibility is one of its greatest strengths, and now you have the tools to take advantage of it.
