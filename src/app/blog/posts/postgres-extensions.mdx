Postgres is a relational database known for its scalability, reliability, and ease of use. It's one of the most popular databases in the world and one of the reasons for its popularity is the ability to extend the database with custom functions, data types and more using the Postgres Extensions API.

In this post, we'll learn to build a Postgres extension from scratch touching upon all the core concepts. This requires some knowledge of C and Postgres.

At its core, a Postgres extension is a collection of 4 files:
1. The `.c` source code file that contains the C code for the extension.
2. A `.sql` file that contains the SQL code for the extension.
3. A `Makefile` that defines how to build the extension.
4. A `.control` file that serves as a manifest and defines the extension name, version, and dependencies.


## The C source file

This is our main source code for the extension. Let's build up our simple "hello world" function by understanding each component first.

#### Header Files

Every PostgreSQL extension starts with including the necessary header files. We need three essential headers:

**`postgres.h`** contains core data types and macros that every extension needs. **`fmgr.h`** handles the Function Manager interface, defining macros like `PG_FUNCTION_ARGS` and `PG_RETURN_*` for function communication. **`utils/builtins.h`** provides utility functions including `cstring_to_text()` for converting C strings to PostgreSQL's text type.

```c
#include "postgres.h"
#include "fmgr.h"
#include "utils/builtins.h"
```

#### PG_MODULE_MAGIC

Next, we need to include a **mandatory** macro that serves as a version check containing information about the PostgreSQL version, architecture, and ABI compatibility details. Without it, PostgreSQL will refuse to load your extension.

```c
PG_MODULE_MAGIC;
```

#### Function Declaration

Before defining our function, we need to register it with PostgreSQL using a macro that declares metadata like the function name and calling convention. Think of it as registering your function with PostgreSQL's function registry.

```c
PG_FUNCTION_INFO_V1(hello_hashlib);
```

#### Function Definition

Our function returns a **`Datum`** (PostgreSQL's universal data type) and takes **`PG_FUNCTION_ARGS`** as input, which contains all function arguments and metadata. Inside the function, `cstring_to_text()` converts our C string to PostgreSQL's internal text type, and `PG_RETURN_TEXT_P()` properly returns the text value.

```c
Datum hello_hashlib(PG_FUNCTION_ARGS)
{
    PG_RETURN_TEXT_P(cstring_to_text("Hello from hashlib extension!"));
}
```

#### The Complete Code

Putting it all together, here's our complete C source file:

```c
#include "postgres.h"
#include "fmgr.h"
#include "utils/builtins.h"

PG_MODULE_MAGIC;

PG_FUNCTION_INFO_V1(hello_hashlib);

Datum hello_hashlib(PG_FUNCTION_ARGS)
{
    PG_RETURN_TEXT_P(cstring_to_text("Hello from hashlib extension!"));
}
```

When someone calls `SELECT hello_hashlib();`, PostgreSQL looks up the function metadata, calls our C function with the standard interface, creates a PostgreSQL text object from our string, and returns it to the user. This demonstrates the fundamental pattern all PostgreSQL extensions follow: receive arguments through the standard interface, process them using PostgreSQL's data types, and return results using PostgreSQL's macros.

## The Control File

The control file serves as a manifest for your extension. It contains metadata that PostgreSQL uses to understand how to install, manage, and interact with your extension. Let's build up our control file step by step.

#### Basic Information

First, we need to provide a description and version for our extension:

```ini
# hashlib extension
comment = 'Simple hash library extension for PostgreSQL'
default_version = '0.0.1'
```

The **`comment`** provides a human-readable description of what your extension does, while **`default_version`** specifies the version to install when no version is specified.

#### Library Path

Next, we tell PostgreSQL where to find our compiled shared library:

```ini
module_pathname = '$libdir/hashlib'
```

**`module_pathname`** points to the compiled shared library. `$libdir` is a PostgreSQL variable that points to the library directory.

#### Schema Configuration

Finally, we configure how the extension behaves in different schemas:

```ini
relocatable = true
```

**`relocatable`** determines whether the extension can be moved to a different schema after installation.

#### Complete Control File

Here's our complete `hashlib.control` file:

```ini
# hashlib extension
comment = 'Simple hash library extension for PostgreSQL'
default_version = '0.0.1'
module_pathname = '$libdir/hashlib'
relocatable = true
```

## The SQL File

The SQL file defines the SQL interface for your extension. It creates the function signatures that map to your C functions. Let's build up our SQL file step by step.

#### Safety Guard

First, we add a safety mechanism to prevent the SQL file from being executed directly:

```sql
-- complain if script is sourced in psql, rather than via CREATE EXTENSION
\echo Use "CREATE EXTENSION hashlib" to load this file. \quit
```

This prevents the SQL file from being executed directly with `psql`. It should only be run through `CREATE EXTENSION`.

#### Function Signature

Next, we define the basic function signature:

```sql
CREATE OR REPLACE FUNCTION hello_hashlib()
RETURNS text
```

**`CREATE OR REPLACE FUNCTION`** defines the SQL function signature, and **`RETURNS text`** specifies that the function returns a text value.

#### Function Implementation

Now we link our SQL function to the C function:

```sql
AS 'MODULE_PATHNAME', 'hello_hashlib'
LANGUAGE C
```

**`AS 'MODULE_PATHNAME', 'hello_hashlib'`** links the SQL function to the C function. `MODULE_PATHNAME` is replaced by the path from the control file. **`LANGUAGE C`** indicates this is a C function.

#### Performance Hints

Finally, we add performance optimization hints:

```sql
IMMUTABLE STRICT;
```

**`IMMUTABLE`** means the function always returns the same result for the same input, and **`STRICT`** means it returns NULL if any argument is NULL.

#### Complete SQL File

Here's our complete `hashlib--0.0.1.sql` file:

```sql
-- complain if script is sourced in psql, rather than via CREATE EXTENSION
\echo Use "CREATE EXTENSION hashlib" to load this file. \quit

CREATE OR REPLACE FUNCTION hello_hashlib()
RETURNS text
AS 'MODULE_PATHNAME', 'hello_hashlib'
LANGUAGE C IMMUTABLE STRICT;
```

## The Makefile

The Makefile defines how to build the extension. Let's build it up step by step to understand each component.

#### Extension Identity

First, we define the basic identity of our extension:

```makefile
EXTENSION = hashlib
MODULE_big = hashlib
```

**`EXTENSION`** is the name of the extension and must match the .control file name. **`MODULE_big`** is the name of the shared library that will be created.

#### Files to Include

Next, we specify which files should be included in the build:

```makefile
DATA = hashlib--0.0.1.sql
OBJS = hashlib.o
```

**`DATA`** lists the SQL files that should be installed with the extension. **`OBJS`** specifies the object files that need to be compiled and linked.

#### Build Configuration

Now we set up the build configuration:

```makefile
PG_CONFIG = pg_config
```

**`PG_CONFIG`** is the path to the pg_config command, which provides build configuration information.

#### PostgreSQL Extension Infrastructure

Finally, we include the PostgreSQL build system:

```makefile
PGXS := $(shell $(PG_CONFIG) --pgxs)
include $(PGXS)
```

**`PGXS`** is the PostgreSQL Extension Building Infrastructure that provides all the build rules and targets we need.

#### Complete Makefile

Here's our complete Makefile:

```makefile
EXTENSION = hashlib
MODULE_big = hashlib
DATA = hashlib--0.0.1.sql
OBJS = hashlib.o 
PG_CONFIG = pg_config
PGXS := $(shell $(PG_CONFIG) --pgxs)
include $(PGXS)
```

## Building with Docker

Instead of installing PostgreSQL development packages locally, we'll use Docker to ensure a consistent build environment.

```dockerfile
ARG PG_MAJOR=17
FROM postgres:$PG_MAJOR
ARG PG_MAJOR

COPY . /tmp/pghashlib
WORKDIR /tmp/pghashlib

RUN apt-get update && \
    apt-get install -y --no-install-recommends \
            build-essential \
            postgresql-server-dev-$PG_MAJOR && \
    make clean && \
    make OPTFLAGS="" && \
    make install && \
    cd / && \
    rm -rf /tmp/pghashlib && \
    apt-get purge -y build-essential postgresql-server-dev-$PG_MAJOR && \
    apt-get autoremove -y && \
    rm -rf /var/lib/apt/lists/*
```

Here's what each step does:

1. **`ARG PG_MAJOR=17`** - Sets the PostgreSQL major version (17 in this case)
2. **`FROM postgres:$PG_MAJOR`** - Uses the official PostgreSQL Docker image
3. **`COPY . /tmp/pghashlib`** - Copies our extension source code into the container
4. **`apt-get install`** - Installs the necessary build tools and PostgreSQL development headers
5. **`make clean && make OPTFLAGS="" && make install`** - Builds and installs the extension
6. **Clean up** - Removes build dependencies and temporary files to keep the image size small

## Building and Testing

### 1. Build the Extension

```bash
# Build the Docker image
docker build -t postgres-hashlib .

# Run the container
docker run -d --name postgres-test \
  -e POSTGRES_PASSWORD=password \
  -p 5432:5432 \
  postgres-hashlib
```

### 2. Connect and Test

```bash
# Connect to the database
docker exec -it postgres-test psql -U postgres

# Create the extension
CREATE EXTENSION hashlib;

# Test the function
SELECT hello_hashlib();
```

You should see the output:
```
           hello_hashlib            
-----------------------------------
 Hello from hashlib extension!
```

## Key Takeaways

1. **Extensions are Powerful** - They allow you to add custom functionality directly to PostgreSQL
2. **Four Essential Files** - Every extension needs a .c file, .sql file, .control file, and Makefile
3. **Version Management** - Extensions support versioning through the control file and SQL scripts
4. **PGXS Simplifies Building** - The PostgreSQL Extension Building Infrastructure handles most of the complexity
5. **Docker for Consistency** - Using Docker ensures reproducible builds across different environments

## Best Practices

- **Always include PG_MODULE_MAGIC** - Without it, PostgreSQL won't load your extension
- **Use proper PostgreSQL data types** - Don't mix C types with PostgreSQL types
- **Handle memory management carefully** - Use PostgreSQL's memory contexts
- **Test thoroughly** - Extensions run in the database process, so bugs can crash the server
- **Version your extensions** - Plan for updates and migrations from the beginning

## Conclusion

Creating PostgreSQL extensions opens up endless possibilities for extending your database's capabilities. From simple utility functions to complex data types and operators, extensions allow you to implement performance-critical functionality directly in the database server.

The pattern we've explored - C functions wrapped in SQL interfaces, managed through control files and built with PGXS - forms the foundation for all PostgreSQL extensions. Whether you're building a simple hash function or a complex full-text search engine, these same principles apply.

Start with simple functions like our hello world example, then gradually add more complex functionality as you become comfortable with the PostgreSQL extension API. The database server's extensibility is one of its greatest strengths, and now you have the tools to take advantage of it.
